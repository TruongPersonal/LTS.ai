**Track:** ReactJS **Độ khó trong track:** Nâng cao **Topic:** Side effect cho server interaction, Axios library, instance pattern, request/response config, interceptor chain, cancellation với AbortController **Mục tiêu:** Hiểu cách React tương tác với server qua side-effect lifecycle; thành thạo Axios instance/config/interceptor pattern để quản lý HTTP request tập trung; kiểm soát cancellation để tránh memory leak và race condition **Prerequisite:** React hooks cơ bản (useState, useEffect, useRef), React component lifecycle, async/await, REST API căn bản. ## 4. Theory

### 4.1 Side Effect trong React

"Side effect" là bất kỳ hành động nào vượt ra ngoài phạm vi render thuần của component: gọi API, đọc/ghi DOM, set interval, log.

**React 18 Strict Mode:** Trong development, React gọi useEffect hai lần (mount → unmount → mount) để phát hiện side-effect không được cleanup đúng cách. Đây là tính năng, không phải bug.

Strict Mode lifecycle: mount → effect chạy unmount → cleanup chạy mount → effect chạy lại (chứng minh cleanup hoạt động)

Nếu effect của bạn gọi API và không cleanup, nó sẽ gọi API hai lần — và đó là cách React nói "bạn quên cleanup kìa".

### 4.4 Interceptor Chain — runtime execution trace

Interceptor là hàm được xếp thành chain và thực thi tuần tự. Mỗi interceptor nhận đầu ra của interceptor trước làm đầu vào.

Request chain (thứ tự chạy với unshift — đăng ký sau chạy trước): interceptor[2]: log → console.log('Request:', config) interceptor[1]: thêm timestamp → config.headers['X-Request-Time'] = Date.now() interceptor[0]: thêm token → config.headers.Authorization ='Bearer xyz' ↓ dispatchRequest (gửi HTTP)

Response chain: dispatchRequest (nhận response) ↓ interceptor[0]: parse data → response.data interceptor[1]: check status → if (response.status === 401) refresh token interceptor[2]: log → console.log('Response:', response) ↓ response (đến.then())

**Quan trọng:** Vì request interceptor dùng chain.unshift(), request interceptor đăng ký **sau** chạy **trước** (reverse-order). Response interceptor dùng chain.push(), chạy theo thứ tự đăng ký. Axios 1.x dùng promise chain — mỗi interceptor là một.then() tuần tự:

### 4.6 React + Axios lifecycle — toàn cảnh

Component mount → useState tạo state → useEffect chạy (lần 1) → Tạo AbortController → Axios.get('/products', { signal: controller.signal}) → request interceptor chain (thêm token, log...) → dispatchRequest (gửi HTTP request) → (chờ response...) → JSX render (loading state)

Component update (deps thay đổi) → cleanup effect cũ: controller.abort() → request bị hủy → effect mới chạy → controller mới → request mới

Component unmount → cleanup effect: controller.abort() → request bị hủy → component bị xóa khỏi DOM → không setState nào được gọi trên component đã mất

### Bước 4: Custom hook useApi — tích hợp cancellation

// hooks/useProducts.js import { useState, useEffect, useRef} from'react'; import apiClient from'../api/client';

export function useProducts(searchQuery ='') { const [products, setProducts] = useState([]); const [loading, setLoading] = useState(true); const [error, setError] = useState(null);

useEffect(() => { const controller = new AbortController(); setLoading(true); setError(null);

apiClient.get('/products', { signal: controller.signal, params: searchQuery? { q: searchQuery} : {}, }) .then(res => { setProducts(res.data); setLoading(false); }) .catch(err => { if (axios.isCancel(err)) { console.log('Request canceled:', err.message); return; // Không setState khi cancel } setError(err); setLoading(false); });

// Cleanup: hủy request khi unmount hoặc searchQuery thay đổi return () => { controller.abort(); }; }, [searchQuery]); // dependency là searchQuery → effect chạy lại khi search

return { products, loading, error}; }

#### Vấn đề giải quyết:

Cleanup abort → không memory leak searchQuery trong deps → effect chạy lại khi search → cancel request cũ → không race condition axios.isCancel(err) phân biệt cancel vs lỗi thật

## <u>9. Bài tập tự luyện</u>

### Dễ

**aài 1:** Tạo một Axios instance với baseURL ='[https://jsonplaceholder.typicode.com'](https://jsonplaceholder.typicode.com') và dùng nó để fetch posts từ /posts. In response ra console.

**aài 2:** Thêm request interceptor vào instance trên để log method + URL của mọi request.

**aài 3:** Thêm response interceptor vào instance để log status code của mọi response.

### Trung bình

**aài 4:** Tạo custom hook useFetch(url, options) nhận URL và options (bao gồm signal), trả về { data, loading, error}. Dùng hook này trong component, kiểm tra trên DevTools Network tab xem request có bị cancel khi component unmount không.

**aài 5:** Sửa race condition: tạo một component search users từ API /users?q=.... Khi gõ nhanh, dùng DevTools Network tab để xác nhận request cũ bị cancel trước khi request mới chạy. (Gợi ý: dùng network throttling thành Slow 3G để thấy rõ).

**aài 6:** Viết response interceptor xử lý lỗi 401: nếu gặp 401, thử refresh token bằng cách gọi /auth/re fresh, nếu refresh thành công thì retry request gốc. (Giả định: refresh token lưu trong localStorag

e.getItem('refreshToken') ).
### Khó

**aài 7:** Xây dựng một hệ thống gồm: Axios instance + request interceptor (attach token + add timestamp header) + response interceptor (401 → refresh token + retry; 5xx → retry tối đa 2 lần với exponential backoff). Viết unit test cho từng interceptor bằng Jest.

**aài 8:** Phân tích memory leak: dùng React DevTools Profiler ghi lại session, tạo component mount/unmount nhanh nhiều lần. Xác nhận không có console warning "Can't perform a React state update on an unmounted component" và không có request pending trong Network tab sau khi unmount.

**aài 9:** So sánh 2 approaches: (a) cancellation bằng AbortController per-effect, (b) dùng useRef lưu latest controller và chỉ abort controller cũ khi effect chạy lại (không abort khi unmount). Giải thích approach nào đúng, approach nào gây memory leak, kèm diagram runtime execution trace.

### P13 — Điều dễ sai nhất:

**"Cleanup function của useEffect chỉ chạy khi component unmountA"** — Sai.

Cleanup chạy **trước khi effect chạy lại lần tiếp theo**, bao gồm cả khi component unmount VÀ khi dependency thay đổi. Đây là lý do chính mà cancellation hoạt động để fix race condition:

Effect với deps=[searchQuery]: Lần 1: searchQuery = "" → effect chạy → tạo controller → API call Lần 2: searchQuery = "ip" → cleanup chạy (abort!) → effect chạy → controller mới → API call mới Lần 3: unmount → cleanup chạy (abort!) → kết thúc

Nếu cleanup chỉ chạy khi unmount, race condition không thể fix được bằng AbortController.
