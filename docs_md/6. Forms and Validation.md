# React 06 — Forms and Validation

**Track:** ReactJS **Độ khó trong track:** Trung bình **Topic:** Controlled components, uncontrolled components, form validation patterns, form submission lifecycle **Mục tiêu:** Hiểu cách React quản lý form state qua controlled vs uncontrolled components, xây dựng validation pattern linh hoạt, và biết khi nào chọn approach nào **Prerequisite:** React 01 (Component & JSX), React 02 (State & re-render) **Version/môi trường giả định:** React 18.x, JavaScript ES2022+, trình duyệt hiện đại (Chrome/Firefox/Edge)

## 1. Problem Context

##### Neo — Tình huống thực tế

Bạn xây trang đăng ký cho một ứng dụng SaaS. Form gồm: họ tên, email, mật khẩu, xác nhận mật khẩu, và dropdown chọn vai trò (Admin/Member). Khi người dùng nhập sai — email thiếu @, mật khẩu quá ngắn — bạn cần hiển thị lỗi ngay bên dưới field tương ứng, và chỉ cho phép submit khi mọi thứ hợp lệ.

##### Manual — Suy nghĩ naïve

Làm theo cách quen thuộc từ HTML thuần: mỗi input có onchange listener, viết hàm validate riêng, gán class lỗi vào DOM element bằng document.querySelector + classList.add. Mỗi lần submit gọi preventDefault(), đọc value từ form elements bằng document.getElementById, kiểm tra điều kiện, show error.

##### Điểm gãy — State phân tán, không đồng bộ

Sau vài tuần feature mới: thêm field "số điện thoại", thêm "xác nhận đồng ý điều khoản" (checkbox), thêm "chọn gói" (radio). Mỗi field có logic validate riêng. Code validate nằm rải rác: một phần trong on change inline, một phần trong onsubmit. Bug xuất hiện: lỗi cũ vẫn hiện sau khi đã sửa, form submit được dù còn lỗi, giá trị field không đồng bộ với UI. Khó debug vì state của form nằm rải rác trong DOM, không có một nơi duy nhất kiểm tra "form có hợp lệ không".

##### Cầu nối — React cần một cách quản lý form state tập trung

React tuyên bố "state là single source of truth". Với form cũng vậy: giá trị mỗi input, trạng thái lỗi, trạng thái "đã touched hay chưa" — tất cả đều nên nằm trong state React, không nằm trong DOM. Đó là tư duy **controlled component**. Nhưng không phải form nào cũng cần controlled — có trường hợp **uncontrolled component** (dùng ref) lại đơn giản hơn.

## <u>2. Old Approach — Làm form theo cách HTML thuần</u>

### Cách làm cũ version 1: DOM-centric thuần túy

Email: <input type="email" id="email" /> <span id="emailError" class="error hidden">Email không hợp lệ</span> </div> <button type="submit">Đăng ký</button> </form>

**Vấn đề:** Mỗi lần submit phải query DOM lại. Error state gắn chặt vào DOM — muốn clear error phải query từng span, thêm/xóa class thủ công. Không có chỗ nào lưu "trạng thái tổng thể của form".

### Cách làm version 2: React nhưng chưa controlled (vẫn dùng DOM cho value)

Khi mới chuyển sang React, một lỗi phổ biến là viết React component nhưng vẫn query DOM để lấy value:

**Tại sao version 2 này vẫn chưa tốt?** Dù đã dùng JSX và React component, giá trị vẫn nằm trong DOM (đọc qua getElementById ), React không quản lý value. Nếu component re-render vì state khác (ví dụ toggle một section), React không biết gì về giá trị input — defaultValue chỉ dùng một lần lúc mount. Muốn validate realtime, phải tự gán onChange listener + DOM manipulation như version 1. Đây là giai đoạn "viết React nhưng nghĩ DOM" — thường gặp ở dev mới chuyển từ jQuery/vanilla JS.

### Form submission lifecycle

User click Submit → e.preventDefault() → Validate tất cả field (validateAll) → Nếu có lỗi: → setErrors({...tất cả lỗi}) → setTouched({...tất cả true}) // hiện mọi lỗi → focus vào field lỗi đầu tiên → Dừng, không submit → Nếu không lỗi: → build data object từ state → gọi API (fetch/POST) → xử lý response (thành công/thất bại) → reset form hoặc chuyển trang

Bất kỳ bước nào trong lifecycle cũng có thể gây lỗi — xem bảng dưới.

**N/A note — P9 (Attribute/Decorator side-effects):** Topic này (React Forms) không có attribute/decorator quan trọng đặc thù cần giải thích side-effects riêng. Các prop form cơ bản ( value, onChange, checked, name ) đã được giải thích trong luồng dữ liệu controlled/uncontrolled ở trên. Các gotcha liên quan tới attribute ( checked vs value trên checkbox, defaultValue vs value ) đã được liệt kê ở phần P10 và P12.

**N/A note — P11 (CLI-first):** Topic React Forms là về component pattern và validation logic trong React, không liên quan tới CLI tool. Các lệnh CLI (npx create-react-app, npm start, vite) thuộc về bài khác (Build Tooling track) và không cần thiết cho nội dung form handling.

### Bước 3: Thêm validation + error state + touched

import { useState} from'react';

// Validation rules function validateForm(values) { const errors = {};

if (!values.name.trim()) errors.name ='Họ tên không được để trống'; else if (values.name.trim().length < 2) errors.name ='Họ tên phải ≥ 2 ký tự';

if (!values.email.trim()) errors.email ='Email không được để trống'; else if (!/^[^\s@]+@[^\s@]+.[^\s@]+$/.test(values.email)) errors.email ='Email không đúng định dạng';

if (!values.password) errors.password ='Mật khẩu không được để trống'; else if (values.password.length < 8) errors.password ='Mật khẩu phải ≥ 8 ký tự'; else if (!/[A-Z]/.test(values.password)) errors.password ='Mật khẩu phải có chữ ho a'; else if (!/\d/.test(values.password)) errors.password ='Mật khẩu phải có số';

if (!values.confirm) errors.confirm ='Xác nhận mật khẩu không được để trống'; else if (values.password!== values.confirm) errors.confirm ='Mật khẩu không khớ p';

if (!values.terms) errors.terms ='Bạn phải đồng ý điều khoản';

return errors; }

### Runtime execution trace (P7)

Khi user gõ email sai "abc" rồi blur:

Lần 0: values.email = "" → touched.email = false → errors.email = undefined (chưa hiện lỗi)

User gõ "a": Lần 1: values.email = "a" → touched.email = false → errors.email = undefined (touched=false nên onChange không validate email)

User blur (rời focus): Lần 2: handleBlur('email') → touched.email = true validateForm({...values, email: "a"}) → errors.email = "Email không đúng địn h dạng" setErrors({ email: "Email không đúng định dạng"}) → re-render → hiển thị lỗi đỏ

User gõ "a@b": Lần 3: values.email = "a@b" → touched.email = true → validateInline /^...$/.test("a@b") → false → errors.email = "Email không đúng định dạng" (lỗi vẫn còn)

User gõ "a@b.co": Lần 4: values.email = "a@b.co" → /^...$/.test("a@b.co") → true → errors.email = undef ined re-render → lỗi biến mất

### Tại sao validation chỉ chạy khi touched? (Thiết kế có chủ đích)

Nếu không có touched, khi validateForm chạy ở lần render đầu tiên, tất cả error đều hiện — form đầy đỏ trước khi user kịp gõ gì. UX cực tệ.

##### Với touched :

Field chưa touched → không hiện lỗi (dù sai) Field đã touched → hiện lỗi + validate realtime Submit → tất cả thành touched → hiện mọi lỗi

Đây là pattern phổ biến trong thư viện form (React Hook Form, Formik) và cũng là behavior mặc định của HTML5 validation.

// Sync errors mỗi khi values đổi (debounced 300ms) useEffect(() => { const timer = setTimeout(() => { const validationErrors = validateFn(values); const mergedErrors = Object.keys(touched).reduce((acc, key) => { if (touched[key]) acc[key] = validationErrors[key]; return acc; }, {}); setErrors(mergedErrors); }, 300); return () => clearTimeout(timer); }, [values, touched]); // eslint-disable-line react-hooks/exhaustive-deps

function handleSubmit(onSuccess) { return (e) => {

e.preventDefault(); const allErrors = validateFn(values); setErrors(allErrors); const allTouched = Object.keys(values).reduce((a, k) => ({...a, [k]: true}),
{}); setTouched(allTouched); if (Object.keys(allErrors).length === 0) onSuccess(values); }; }
