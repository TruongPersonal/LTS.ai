# React 07 — Dynamic Components: Form & Table

**Track:** ReactJS **Độ khó trong track:** Trung bình **Topic:** Dynamic form generation từ config, dynamic table với column config, render props, composition pattern, generic reusable component **Mục tiêu:** Hiểu cách xây dựng component React có thể tái sử dụng ở mức cấu hình (config-driven), phân biệt dynamic rendering vs hard-coded component, nắm pattern render props và composition để tạo Form và Table linh hoạt **Prerequisite:** React 04 — Basic Hooks (useState, useEffect), React 06 — Forms and Validation, JavaScript array methods (map, filter, reduce) **Version/môi trường giả định:** React 18.x, JavaScript ES2022+, trình duyệt hiện đại (Chrome/Firefox/Edge)

## 1. Problem Context

##### Neo — Tình huống thực tế

Bạn xây một dashboard quản lý nhân sự cho công ty ~200 người. Dashboard có:

Form thêm nhân viên mới: họ tên, email, phòng ban, chức vụ, ngày vào làm, mức lương, trạng thái thử việc, ghi chú... Bảng danh sách nhân viên: hiển thị tất cả employee fields, có sort theo từng cột, filter theo phòng ban/chức vụ, search theo tên

Tuần sau, sếp nói: "Thêm form quản lý dự án đi — tên dự án, mô tả, ngày bắt đầu/kết thúc, danh sách thành viên, priority." Tuần sau nữa: "Thêm bảng danh sách dự án nữa, sort theo priority, filter theo trạng thái."

Mỗi lần thêm một form hoặc bảng mới, bạn copy code từ cái cũ, đổi tên field, sửa JSX. Sau 3-4 lần, code bắt đầu có mùi.

##### Manual — Suy nghĩ naïve

Lập trình viên React mới thường làm: tạo một component cứng cho từng form. Mỗi field là một <input> riêng trong JSX, mỗi <th> trong table là một thẻ riêng. Khi cần form mới, copy toàn bộ file, đổi tên component, sửa từng dòng JSX cho khớp với fields mới.

##### Điểm gãy — Copy-paste không scale được

Sau 5 form + 5 bảng, bạn có 10 component gần giống nhau. Bug xuất hiện:

Quên một validation rule ở form mới vì copy thiếu Sửa style ở form cũ nhưng quên cập nhật form mới Bảng mới thiếu cột sort vì quên thêm handler Thêm field "số điện thoại" vào employee form nhưng quên thêm vào employee table

Mỗi lần sửa một chỗ, phải nhớ sửa ở N chỗ khác. Đây là dấu hiệu "copy-paste programming" — vi phạm DRY (Don't Repeat Yourself) ở cấp độ component.

##### Cầu nối — Config-driven component thay vì hard-code

React cho phép render JSX từ dữ liệu động qua Array.map() và các pattern composition. Thay vì viết từng <input> trong JSX, ta viết **một** component Form nhận một mảng config FieldConfig[] và tự sinh ra các field tương ứng. Tương tự, Table nhận ColumnConfig[] + data array và tự render bảng.

Đây không phải thư viện mới — đây là cách React được thiết kế để dùng: component là function nhận props, và props có thể là "cấu hình" mô tả UI cần sinh ra.

## <u>3. Weakness — Minh họa bằng tình huống cụ thể</u>

### Weakness 1: Thay đổi layout ảnh hưởng N component

Công ty đổi thiết kế: tất cả label chuyển lên trên input (vertical form) thay vì nằm ngang. Với hard- code form, phải vào từng component, sửa từng <label> wrapper:

**Hậu quả:** Thiếu nhất quán — EmployeeForm đã sửa, ProjectForm chưa, QA bug "label format không đồng bộ".

### Weakness 2: Validation logic rải rác

### Weakness 3: Thiếu cột ở bảng mới

Khi thêm field "số điện thoại" vào employee form, team quên thêm cột vào employee table. Users phải mở từng employee để xem số điện thoại. Bug này xuất hiện vì form config và table config là hai nơi riêng biệt — không có một "register" duy nhất cho toàn bộ field của entity.

## <u>4. Theory — Config-driven rendering trong React</u>

## 5. Running Example — Employee Management Dashboard

Xuyên suốt bài này, ta xây một dashboard quản lý nhân viên gồm:

**DynamicForm** — form thêm/sửa employee với fields: name, email, department, role, salary, startDate, isProbation **DynamicTable** — bảng hiển thị danh sách employee với columns: name, email, department, role, salary, status (tính toán từ isProbation + startDate)

Cả hai component đều nhận config là mảng — chỉ cần đổi config là tạo được Form/Table cho entity khác (Project, Client, Task...).

## 7. Case Study

##### [Case minh họa]

**Công ty XYZ** xây dựng internal tool quản lý vận hành gồm 12 entity khác nhau (Employee, Project, Task, Client, Invoice, Contract, Vendor, Asset, Ticket, LeaveRequest, Expense, Report).

**Approach A — Hard-code tất cả:** mỗi entity một Form component riêng + một Table component riêng = 24 component. Trung bình mỗi component 200 dòng → tổng ~4800 dòng. Thêm một field: sửa 2 file. Thay đổi validation pattern: sửa 12 file.

**Approach B — Config-driven dynamic:** 2 component (DynamicForm + DynamicTable) + 12 config arrays (~30 dòng/entity) = 2 component × 150 dòng + 12 × 30 dòng = 660 dòng. Thêm một field: thêm 1 dòng vào config. Thay đổi validation pattern: sửa 1 chỗ trong DynamicForm.

##### Kết quả sau 6 tháng phát triển:

Approach A: 24 component, ~4800 dòng, 37 bug liên quan đến copy-paste inconsistency Approach B: 2 component, ~660 dòng, 4 bug (chủ yếu ở custom render không handle edge case) Time to add new entity: Approach A mất 2-3 ngày (copy, sửa, test), Approach B mất 3-4 giờ (viết config + test)

**Bài học:** Config-driven rendering không chỉ tiết kiệm code — nó **giảm diện tích bề mặt cho bug** (surface area for bugs) bằng cách tập trung logic vào một chỗ thay vì phân tán qua N bản copy.

### Behavior đặc trưng cần biết (P12)

**Dynamic children + key prop** — React dùng key để match element tree giữa các render. Nếu DynamicForm fields thay đổi thứ tự, React sẽ **move** DOM nodes thay vì destroy + recreate, nhờ key ổn định. **Controlled input của dynamic form** — Mỗi <input value={formData[field.name]} onChange ={...}> là controlled Component. Giá trị hiển thị luôn đến từ state, không từ DOM. Nếu quên onC hange, input sẽ **không thể gõ được**. **DynamicTable + column.render** — Function render được tạo mới mỗi lần render, nhưng chỉ ảnh hưởng tới cell nào thực sự gọi nó. React DevTools không phân biệt được "render function đổi reference" vs "render result đổi" — nên dùng React.memo nếu performance critical.

### Điểm dễ hiểu sai nhất (P13)

***Sai diễn giải phổ biến:** "Dynamic components nghĩa là dùng eval() hoặc createElement* *thủ công để tạo component từ string config."* ***Thực tế:** Dynamic component trong React đơn giản là dùng Array.map() để render JSX từ dữ* *liệu. Không cần eval(), không cần dangerouslySetInnerHTML. Config là mảng object,* *component duyệt mảng đó và trả về JSX tương ứng. Đây là tính năng cơ bản nhất của React —* *JSX là JavaScript, và JavaScript có thể duyệt mảng.*

## <u>9. Bài tập tự luyện (P4)</u>

### Dễ

**Bài A:** Tạo FieldConfig cho form đăng ký newsletter gồm: email (required, pattern email), frequency (select: daily/weekly/monthly), acceptTerms (checkbox required).

**Bài 2:** Dùng DynamicForm với config trên, render form trong App. Submit log formData ra console. Chạy trong trình duyệt, mở Console để kiểm tra.

**Bài 3:** Với DynamicTable, tạo ColumnConfig cho data array users = [{id:1, name:"Alice", age:30}, {id:2, name:"Bob", age:25}]. Cột "name" sortable, cột "age" sortable.

### Trung bình

**Bài 4:** Mở React DevTools → Components tab. Chọn DynamicForm instance, quan sát formData state. Nhập vào input — state có thay đổi không? Xóa input — state có reset không? Note lại behavior.

**Bài 5:** DynamicForm hiện tại dùng value cho text input nhưng checked cho checkbox. Nếu viết FieldRenderer dùng checked cho cả text input thì chuyện gì xảy ra? Dùng thử, quan sát Console warning, giải thích.

**Bài 6:** Thêm cột "Actions" vào DynamicTable với custom render chứa button "Xóa". Button onClick in ra console row data. Verify bằng cách click và quan sát Console.

**Bài 7:** DynamicForm thiếu chức năng "reset form" sau submit. Thêm button "Reset" gọi setFormData về initial values. Kiểm tra bằng cách nhập dữ liệu → Reset → xem formData trong React DevTools.

**Bài 8:** Viết search filter cho DynamicTable — thêm input "Tìm kiếm" phía trên table, lọc data khi gõ. Dùng useMemo để tránh sort + filter conflict.

### Khó

**Bài 9:** DynamicForm hiện tại chỉ validate trên blur và submit. Thêm real-time validation (validate ngay khi user gõ) nhưng chỉ sau khi field đã touched lần đầu (tránh show error ngay khi mới focus). Dùng React DevTools để verify error state thay đổi đúng lúc.

**Bài A0:** Xây FilterableTable kết hợp DynamicTable + filter bar. Filter bar gồm các dropdown được sinh từ config filterFields. Mỗi dropdown filter data theo field tương ứng. Test với data 50 employees, verify filter kết hợp nhiều điều kiện.

**Bài AA:** DynamicForm dùng useEffect để reset form khi config thay đổi. Nếu không có useEffect, form sẽ giữ state cũ khi chuyển entity — dẫn đến bug "dữ liệu cũ hiện trên form mới". Viết test mental: tạo TimerForm và TaskForm, chuyển giữa chúng, kiểm tra có thấy field của form cũ không. Giải thích tại sao.

## 10. Recap

Dynamic components — Form và Table — là áp dụng cốt lõi của tư duy **"component là function của** **props"** trong React:

**aorm** = f(fields: FieldConfig[]) → JSX **Table** = f(data: T[], columns: ColumnConfig[]) → JSX

##### 3 nguyên tắc vàng:

1. **Config-driven không phải magic** — chỉ là Array.map() render JSX từ dữ liệu
2. **Key prop quyết định DOM reconciliation** — dùng stable key (field.name, row.id), không dùng index
3. **Composition lấp đầy gap config** — children slot cho phần custom mà config không cover được
##### Khi nào dùng:

≥3 entity cùng pattern → dynamic 1-2 entity, ít thay đổi → hard-code Layout phức tạp → composition + dynamic hybrid

## 11. Góc nhìn nâng cao

### Từ DynamicForm đến Form Library

Các thư viện form React (React Hook Form, Formik, React Final Form) đều dùng config-driven pattern nhưng mở rộng thêm:

**Unregister field khi unmount** — field conditional render không để lại state cũ **Touched/dirty tracking** — biết field nào đã được người dùng chạm vào **Async validation** — gọi API kiểm tra email đã tồn tại chưa **Schema validation** — dùng Yup/Zod schema thay vì custom validation object

DynamicForm trong bài này là phiên bản tối giản — hiểu được nó, bạn hiểu được architecture của các form library.

### Từ DynamicTable đến Data Grid

Ag-Grid, MUI Data Grid, React Table (TanStack Table) mở rộng DynamicTable với:

**Virtual scrolling** — chỉ render rows trong viewport, không render 10,000 rows **Column grouping** — header nhiều cấp **Inline editing** — click cell để edit **Row selection + bulk actions** **Server-side sorting/pagination** — sort/filter gửi lên server

DynamicTable tự xây được cho đến ~1000 rows; trên mức đó cần virtualization.

### Generic component với TypeScript

// DynamicTable generic — T là type của mỗi row function DynamicTable<T extends { id: string | number}>({ data, columns, }: { data: T[]; columns: ColumnConfig<T>[]; }) {...}

// Dùng — TypeScript tự suy ra type của row const employeeColumns: ColumnConfig<Employee>[] = [...]; <DynamicTable data={employees} columns={employeeColumns} />

Generic giúp mỗi cột chỉ truy cập được đúng key của entity đó — TypeScript báo lỗi nếu viết col.key = 'nonexistent'.
